01 · The model

Arches: open source, standards-based

Open-source data management, developed with the Getty Conservation Institute and World Monuments Fund for a hard problem: describing cultural heritage.

  • Uncertain dates, fuzzy extents, dense relationships
  • Records that must outlive the software
  • Los Angeles' own inventory, HistoricPlacesLA, runs on it

AGPL-3.0, OSS stack

PostgreSQL/PostGIS, Django

Ontology-backed

Each graph can be based on known ontologies such as CIDOC CRM (ISO 21127)

Vocabularies, linked data

SKOS thesauri; JSON-LD export

The demo uses the community's open arches-her models, plus a few US terms.

⏱ 2:00 to 2:45

  • Built for heritage because heritage is hard: uncertain, relationship-dense, long-lived.
  • HistoricPlacesLA, the City's historic resources inventory and the source of the Rancho Vega photo, is an Arches deployment. Say so: the story isn't hypothetical.
  • Point at the stack card: it runs on what this room already runs. If asked about the map library: MapLibre from Arches 8.2 (upcoming); 8.1 still ships mapbox-gl 1.13, the last BSD-licensed release.
  • Standards in one breath: CIDOC CRM for meaning, SKOS for terms, JSON-LD out. Not a lesson in CIDOC CRM.
  • arches-her: models built for Historic Environment Records in England.

01 · The model

Keep your features: Arches speaks GIS

  • PostGIS: geometry lives with the rest of your data
  • Spatial views: open in QGIS; publish with GeoServer or pg_featureserv
  • APIs: GeoJSON, vector tiles
  • GIS plugins for QGIS (QGIS 3 for now) and GeoLibre (experimental, Arches 8.2) edit geometries directly in your GIS

⏱ 3:30 to 4:15

  • "Features are fast, familiar and powerful. Keep them. Arches stores geometry in PostGIS; the question is where the context lives."
  • Point at the QGIS table: an ordinary PostGIS view, but the architect column is a relationship, not a field anyone typed in. The view has a designation column too; it's hidden in the screenshot, because which of his works aren't landmarks is the demo's question.
  • On the right, the Arches QGIS plugin (archesproject/arches-qgis): signed in to the demo as a contributor, with Rancho Vega selected as the resource to edit. It adds or replaces a resource's geometry from any QGIS feature (the Add and Replace geometry buttons), through the Arches API, with Arches permissions. Say plainly that it needs QGIS 3 (it imports PyQt5); a QGIS 4 / Qt6 port is one of the asks on slide 11. The screenshot is QGIS 3.44 LTR.
  • OGC: Arches doesn't serve OGC APIs itself. Its spatial views are plain PostGIS, so GeoServer or pg_featureserv can publish them. A native OGC API Features endpoint is on the help-wanted list (slide 11).
  • The table only holds works with polygons. Two more undesignated LA works (UCLA La Kretz, Hahn Hall) are points; they show up in the demo query.
  • Be candid: the GeoLibre plugin is experimental and depends on Arches 8.2, which hasn't been released yet.

03 · The payoff

Self-describing, not just legible

In a flat table

BLT_BY: "P. Williams"
  • Who? A person record with a stable id, not a name string
  • What relationship? P14 carried out by, a published definition
  • In what role? Architect, a vocabulary term

An AI agent can follow P14 carried out by. It can only guess what BLT_BY means.

The same fact, exported from Arches as JSON-LD

{
  "@type": "crm:E18_Physical_Thing",
  "crm:P12i_was_present_at": {
    "@type": "crm:E7_Activity",
    "crm:P9_consists_of": {
      "@type": "crm:E7_Activity",
      "crm:P14_carried_out_by": {
        "@id": ".../resources/8ec6c939-…",
        "@type": "crm:E21_Person"
      },
      "crm:P2_has_type": { "rdfs:label": "Architect" }
} } }

Rancho Vega's real export, one path kept.

⏱ 13:00 to 14:15

  • Left: what most systems store. Right: what Arches exports for the same fact. It's the real export with one path kept: tile ids removed, namespaces shortened, whitespace compacted, nothing reordered.
  • Don't read the JSON. The dimmed lines are structure; the highlighted ones answer the three questions on the left.
  • "Who is P. Williams? Which one? In what role? The export answers all three without a data dictionary." Point at each: the @id is a Person record, not a string; P14 has a published CIDOC CRM definition; Architect is a vocabulary term.
  • "BLT_BY is legible to whoever made the table. This is self-describing: it carries its own meaning."
  • AI, concretely: hand an agent the question from the demo, "which of Williams's works aren't landmarks?" With this export it follows P14 to a Person with a stable id and checks the designation type. With the flat table it has to guess that BLT_BY is an architect and that "P. Williams" is the same person everywhere.
  • The same explicit structure is what makes the data FAIR for people: findable, interoperable, reusable.
  • If a CIDOC CRM person asks: the inner activity is arches-her's grouping for associated actors; the construction itself is an E11 Modification linked with CRMsci O18i.
